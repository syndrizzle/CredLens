# P2-01 / P2-02 / P2-04 persistence, authentication, and revision contract

The user selected FastAPI-managed accounts (`D-03`). P2-01 established internal owner UUIDs and the five financial tables; P2-02 added `accounts`, `sessions`, `scrypt` password hashing, cookie-backed server sessions, and owner-scoped workspace API/UI integration; P2-04 adds reviewer tracking (`figures.reviewed_by`), immutable input revision history (`revisions`), optimistic concurrency (`PUT /api/businesses/{business_id}`), and automatic supersession of earlier analysis runs.

Scope: Alembic migrations (`2b45e0cd055f`, `7c84f91a3d02`, and `c491e82a10bf`), backend persistence and authentication modules (`app/persistence.py`, `app/auth.py`), and protected workspace routes (`app/main.py`) connected to the entry/review UI (`src/features/manual-entry/ManualEntry.tsx`). The stateless `POST /api/validate` and `POST /api/analysis` routes remain available for unauthenticated fictional-data prototype use and Phase 1 tests.

- Owners: internal UUID, creation time; referenced by accounts, businesses, figure reviews, and input revisions. The demonstration seed (`app/seed.py`) uses a fixed internal owner ID without an `accounts` row and cannot be logged into.
- Accounts: `owner_id` primary/foreign key (`ON DELETE CASCADE`), normalized lowercase email (`unique`, checked for trimmed lowercase and `@`), `password_hash` (`scrypt$16384$8$1$<salt_hex>$<digest_hex>` using Python standard-library `hashlib.scrypt` with 16-byte random salt and `hmac.compare_digest` verification), creation time.
- Sessions: `token_hash` primary key (64-char SHA-256 hex digest of a 256-bit `secrets.token_urlsafe(32)` token; raw token is never stored in PostgreSQL), `owner_id` foreign key (`ON DELETE CASCADE`), `expires_at` (7-day TTL), creation time. Delivered in an `HttpOnly`, `SameSite=Lax`, `Path=/` cookie (`credlens_session`, `Secure` on HTTPS).
- Businesses: owner foreign key, name, INR/standalone basis, monotonically increasing `input_revision` (`> 0`).
- Revisions: (`business_id`, `input_revision`) primary key, `actor_id` foreign key to `owners`, canonical `inputs` JSONB snapshot (including computed per-figure `revision` and `origin: "manual"`), creation time. Written atomically on initial creation (`input_revision = 1`) and every in-place update (`input_revision = current + 1`) so historical input states and figure revisions remain auditable even if periods or figures are later removed and re-entered.
- Periods: business foreign key, unique start year, unit, exact multiplier, comparability confirmation.
- Figures: period/field key, raw text or null, exact normalized INR numeric or null, manual origin, reviewed flag, `reviewed_by` foreign key to `owners` (enforced by `CHECK (reviewed = (reviewed_by IS NOT NULL))`), and server-computed `revision` (`> 0`, incremented whenever `raw` or normalized INR changes relative to the prior period/revision history). Omitted fields remain omitted.
- Analysis runs: business foreign key, input revision, rule version, timestamp, full input snapshot and result JSONB. Results include all six findings, input/revision evidence, reasons, balance checks, and limitations. Decimal values remain strings inside JSON.
- P2-03 adds `action_version: preparation-actions-v1` and grouped preparation actions to new result snapshots. Actions reference input years/fields and affected indicator/balance-check results, ordered as review, missing evidence, interpretation limits, and supported investigation. They are generated from persisted inputs by the same `analyse` path as stateless calculations and survive workspace/run reload. Existing JSONB storage needs no migration. Legacy snapshots remain readable with no action version/list and prompt re-analysis; they are never silently regenerated on read.
- P2-04 adds `PUT /api/businesses/{business_id}` (`UpdateBusinessRequest` with `expected_revision`). `update_business` locks the owned business row (`SELECT ... FOR UPDATE`), verifies `expected_revision == business.input_revision` (returning HTTP `409` on mismatch), computes per-figure revisions server-side against existing periods and historical `revisions` snapshots, increments `business.input_revision`, replaces current periods/figures, and records a new `revisions` snapshot. `WorkspaceResponse` exposes `latest_run_id` and `latest_analysis` only when the newest run matches `business.input_revision` (`null` otherwise, invalidating stale outputs) while returning all historical runs in `runs` (`run_id`, `input_revision`, `rule_version`, `created_at`, `superseded: run.input_revision < business.input_revision`).

Creation and updates are atomic in caller-owned transactions. Every protected route (`GET /api/auth/session`, `GET /api/businesses`, `POST /api/businesses`, `GET /api/businesses/{business_id}`, `PUT /api/businesses/{business_id}`, `POST /api/businesses/{business_id}/analysis`, `GET /api/analysis-runs/{run_id}`) resolves `owner_id` strictly from the verified server session cookie—never from client-submitted payloads. Unknown and other-owner records return identical `404` responses (`Business not found` or `Analysis not found`). Login failures for unknown emails run a constant-parameter dummy `scrypt` verification and return the same `401` (`Invalid email or password`) as wrong passwords.
