# P2-01 / P2-02 / P2-04 / P3-01 / P3-02 persistence, authentication, revision, and document contract

The user selected FastAPI-managed accounts (`D-03`). P2-01 established internal owner UUIDs and the five financial tables; P2-02 added `accounts`, `sessions`, `scrypt` password hashing, cookie-backed server sessions, and owner-scoped workspace API/UI integration; P2-04 and P2-04-F1 add reviewer tracking (`figures.reviewed_by`), immutable input revision history (`revisions`) including populated-upgrade backfill, optimistic concurrency (`PUT /api/businesses/{business_id}`), consistent revision-verified reads/snapshots, and automatic supersession metadata across workspace and direct run endpoints; P3-01 adds protected PDF document storage (`documents` table + `backend/.storage/documents`), type/content/size/page/digital-text validation (`pdfplumber`), single-active-job enforcement, and interrupted-job recovery/retry; P3-02 adds bounded digital-PDF candidate extraction (`app/pdf_extraction.py`) in the parser child, nullable `documents.extraction` JSONB snapshots (`pdf-extraction-v1`, migration `e519a47c8b14`), and owner-protected extraction read/processing routes without modifying financial figures or revisions.

Scope: Alembic migrations (`2b45e0cd055f`, `7c84f91a3d02`, `c491e82a10bf`, `d842f19b6e03`, and `e519a47c8b14`), backend persistence, authentication, and document modules (`app/persistence.py`, `app/auth.py`, `app/documents.py`, `app/pdf_extraction.py`), and protected workspace routes (`app/main.py`) connected to the entry/review UI (`src/features/manual-entry/ManualEntry.tsx`). The stateless `POST /api/validate` and `POST /api/analysis` routes remain available for unauthenticated fictional-data prototype use and Phase 1 tests.

- Owners: internal UUID, creation time; referenced by accounts, businesses, figure reviews, input revisions, and documents. The demonstration seed (`app/seed.py`) uses a fixed internal owner ID without an `accounts` row and cannot be logged into.
- Accounts: `owner_id` primary/foreign key (`ON DELETE CASCADE`), normalized lowercase email (`unique`, checked for trimmed lowercase and `@`), `password_hash` (`scrypt$16384$8$1$<salt_hex>$<digest_hex>` using Python standard-library `hashlib.scrypt` with 16-byte random salt and `hmac.compare_digest` verification), creation time.
- Sessions: `token_hash` primary key (64-char SHA-256 hex digest of a 256-bit `secrets.token_urlsafe(32)` token; raw token is never stored in PostgreSQL), `owner_id` foreign key (`ON DELETE CASCADE`), `expires_at` (7-day TTL), creation time. Delivered in an `HttpOnly`, `SameSite=Lax`, `Path=/` cookie (`credlens_session`, `Secure` on HTTPS).
- Businesses: owner foreign key, name, INR/standalone basis, monotonically increasing `input_revision` (`> 0`).
- Revisions: (`business_id`, `input_revision`) primary key, `actor_id` foreign key to `owners`, canonical `inputs` JSONB snapshot (including computed per-figure `revision` and `origin: "manual"`), creation time. Written atomically on initial creation (`input_revision = 1`), backfilled during migration `c491e82a10bf` for pre-existing populated businesses, and snapshotted before any destructive period replacement in `update_business` (`ON CONFLICT DO NOTHING`) plus at `input_revision = current + 1` so historical input states and figure revisions remain strictly monotonic even if periods or figures are removed and re-entered.
- Periods: business foreign key, unique start year, unit, exact multiplier, comparability confirmation.
- Figures: period/field key, raw text or null, exact normalized INR numeric or null, manual origin, reviewed flag, `reviewed_by` foreign key to `owners` (enforced by `CHECK (reviewed = (reviewed_by IS NOT NULL))`), and server-computed `revision` (`> 0`, incremented whenever `raw` or normalized INR changes relative to the prior period/revision history). Omitted fields remain omitted.
- Analysis runs: business foreign key, input revision, rule version, timestamp, full input snapshot and result JSONB. Results include all six findings, input/revision evidence, reasons, balance checks, and limitations. Decimal values remain strings inside JSON.
- Documents (`P3-01` / `P3-02`): `id` primary key, `business_id` foreign key (`ON DELETE CASCADE`), `owner_id` foreign key (`ON DELETE CASCADE`), sanitized `.pdf` `filename`, 64-character `sha256` hex digest, `byte_size` (`1..20971520` bytes = 20 MB max), `page_count` (`NULL` or `1..50`), `extracted_char_count` (`NULL` or `>= 0`, required `> 0` when `status = 'ready'`), `status` (`processing`, `ready`, `failed`), `error_code`, `error_message`, nullable `extraction` JSONB (`DocumentExtractionSnapshot`, migration `e519a47c8b14`), `created_at`, `updated_at`, and partial unique index `documents_one_active_job_idx` on `(owner_id) WHERE status = 'processing'`. PDFs live under `backend/.storage/documents/<owner_id>/<business_id>/<document_id>.pdf` (configurable via `DOCUMENT_STORAGE_DIR`). P3-01-F1 authenticates/caps raw requests before multipart parsing (20 MB file plus 64 KiB bounded overhead) and rejects extension/MIME/header/empty/file-size errors without insertion or file creation. Accepted basic uploads commit a `processing` row before any file write or expensive parsing; deep validation failures (encryption, malformed structure, no text, page/resource limits) persist `failed` metadata plus the private source file, never a ready/viewable document. Inspection and candidate extraction run in the same isolated local child with 15 s wall / 10 s CPU / 512 MiB memory budgets, lazy traversal stopping before page 51, 8 MiB per decoded page stream / 32 MiB total, 250,000 non-whitespace text characters, 50,000 retained characters per page / 350,000 total (including whitespace), 10 tables and 250 table rows per page / 2,000 total rows, 16 columns, 1,000 characters per cell / 10,000 total cells, 500 candidates, and 2 MiB serialized child stdout. Limits fail closed.

  Validated `extraction` snapshots and `status = 'ready'` publish together in the same final transaction. `processing`, `failed`, `interrupted_job`, and `deletion_pending` states expose no current snapshot (`extraction: null` with explicit `extraction_status`). Pre-P3-02 `ready` rows have `extraction IS NULL` (`extraction_status: "not_extracted"`) and remain viewable; `POST /api/businesses/{business_id}/documents/{document_id}/extract` (or `/extraction`) runs bounded extraction on an owned `ready` document under the per-owner advisory lock without relaxing failed-document `retry` semantics, and replaces the stored snapshot only on success. `DocumentSummary` listings and `WorkspaceResponse.documents` omit full source text and extraction JSON; extraction never writes to `figures`, never confirms values, never advances `businesses.input_revision`, and never invalidates `analysis_runs`.

  Document mutation helpers own short transactions via an `Engine`, coordinated by a per-owner PostgreSQL transaction-scoped advisory lock held on a separate connection throughout the job. This works across backend processes and via transaction pooling; the partial unique index remains. Listing/workspace reads reconcile processing rows only if the advisory lock is free, and set `failed` / `interrupted_job`. A failed final-status commit or actual process death leaves a recoverable row/file; retry uses the stored file. Missing/incomplete storage requires Remove/re-upload. Removal commits `failed` / `deletion_pending` intent before unlinking `.pdf`/`.tmp`, then deletes metadata (including `extraction`). If intent commit fails, no unlink occurs; if unlink or final row deletion fails, the pending record is visible and Remove can finish later. Pending removal cannot be processed or viewed. Refresh status only updates document metadata, preserving unsaved financial inputs. Filesystem power-loss durability and database-backup erasure are not claimed; files stay on the same private backend host. See [backend operation limits](../backend/README.md).
- P2-03 adds `action_version: preparation-actions-v1` and grouped preparation actions to new result snapshots. Actions reference input years/fields and affected indicator/balance-check results, ordered as review, missing evidence, interpretation limits, and supported investigation. They are generated from persisted inputs by the same `analyse` path as stateless calculations and survive workspace/run reload. Existing JSONB storage needs no migration. Legacy snapshots remain readable with no action version/list and prompt re-analysis; they are never silently regenerated on read.
- P2-04 and P2-04-F1 add `PUT /api/businesses/{business_id}` (`UpdateBusinessRequest` with `expected_revision`), consistent revision-verified reads/snapshots, and direct run metadata (`AnalysisRunResponse`). `update_business` locks the owned business row (`SELECT ... FOR UPDATE`), verifies `expected_revision == business.input_revision` (returning HTTP `409` on mismatch), snapshots pre-existing inputs into `revisions` if absent, computes per-figure revisions server-side against `max(prior_figure.revision, max_historical_revision)`, increments `business.input_revision`, replaces current periods/figures, and records a new `revisions` snapshot. `load_business` and `load_workspace` verify `businesses.input_revision` across multi-query reads and retry if a concurrent update committed mid-read; `save_analysis` locks the `businesses` row (`FOR UPDATE`) and reloads under the lock if `input_revision` changed so `analysis_runs.input_revision`, `inputs`, and `results` always agree. `WorkspaceResponse` exposes `latest_run_id` and `latest_analysis` only when the newest run matches `business.input_revision` (`null` otherwise, invalidating stale outputs) while returning all historical runs in `runs` (`run_id`, `input_revision`, `rule_version`, `action_version`, `created_at`, `superseded`) and uploaded `documents` (`DocumentSummary`). `GET /api/analysis-runs/{run_id}` (`load_analysis`) joins `analysis_runs` and `businesses` in one atomic query and returns `AnalysisRunResponse` (`run_id`, `business_id`, `input_revision`, `superseded`, `created_at` alongside the full `AnalysisResponse`).

Financial/account creation and updates are atomic in caller-owned transactions; document writes use the staged, service-owned transactions above. Every protected route (`GET /api/auth/session`, `GET /api/businesses`, `POST /api/businesses`, `GET /api/businesses/{business_id}`, `PUT /api/businesses/{business_id}`, `POST /api/businesses/{business_id}/analysis`, `GET /api/analysis-runs/{run_id}`, `GET /api/businesses/{business_id}/documents`, `POST /api/businesses/{business_id}/documents`, `POST /api/businesses/{business_id}/documents/{document_id}/retry`, `GET /api/businesses/{business_id}/documents/{document_id}/extraction`, `POST /api/businesses/{business_id}/documents/{document_id}/extract`, `POST /api/businesses/{business_id}/documents/{document_id}/extraction`, `GET /api/businesses/{business_id}/documents/{document_id}/file`, `DELETE /api/businesses/{business_id}/documents/{document_id}`) resolves `owner_id` strictly from the verified server session cookie—never from client-submitted payloads. Unknown and other-owner records return identical `404` responses (`Business not found`, `Analysis not found`, or `Document not found`). Login failures for unknown emails run a constant-parameter dummy `scrypt` verification and return the same `401` (`Invalid email or password`) as wrong passwords.

P2-05-F1 protects the populated-upgrade verification itself: it binds Alembic to the direct `PERSISTENCE_TEST_URL`, clears inherited engine caches, and rejects a fixture/DDL target mismatch or Neon pooled URL before migrations run. The selected test database must be disposable because this test downgrades its entire schema. Application env files are unchanged; offline safety regressions intercept migration calls before any database access.
